# nom2.jp 記事自動生成ルーティーン

このスキルは、nom2.jp（日本酒メディア）の記事を1本、リサーチから執筆・商品リンク挿入・画像生成・MicroCMSへの下書き登録まで一気通貫で行う。**公開は絶対にしない**（必ず`status=draft`で保存し、人間の確認を待つ）。

作業ディレクトリはこのプロジェクト直下（`nom2.jpエージェント/`）。ヘルパースクリプトは `lib/*.mjs`、Node.js（ESM）で実装済み。実行は `node -e` またはインラインスクリプトから各関数をimportして呼び出す。

## 手順

### 1. 直近記事の重複チェック
`lib/microcms.mjs` の `listRecent(30)` を呼び、直近記事のタイトル・カテゴリを取得する。これから書くテーマがこれらと似すぎていないか確認する材料にする。

```js
import { listRecent } from "./lib/microcms.mjs";
const recent = await listRecent(30);
```

### 2. 季節・トレンドのリサーチ
実行時点の日付（今日の日付は会話コンテキストから取得できる）を基準に、WebSearchで以下のような切り口を調べる：
- 直近〜今後数週間の日本酒関連ニュース、新酒・限定酒のリリース
- 季節のイベント（酒蔵の蔵開き、日本酒フェス、地域の祭り、二十四節気など）
- 季節に合う飲み方・ペアリング（夏なら冷酒、冬なら燗酒など）
- 直近話題になっている酒蔵・銘柄・トピック

必ず複数の情報源にあたり、一次情報（酒蔵公式・自治体・団体の発表等）を優先する。

### 3. テーマ決定
手順1の直近記事と被らず、季節性・時事性のある切り口を1つ選ぶ。過去記事の傾向（豆知識系「大人の社会科見学」、銘柄紹介、ペアリング、地域特集など）を踏まえて多様性を持たせる。

**注意（話題性の確認）**: 特定の新商品・クラウドファンディング・個別イベントなど「ニッチで具体的なニュース」を主役に据える場合は、それが実際に注目されているか（支援者数・レビュー数・複数メディアでの言及量など）を確認する。話題性が乏しい場合は、その固有名詞を記事の主役にせず、より一般的・汎用的なテーマ（例：個別の新商品名ではなく「熟成日本酒×肉のペアリング」のような切り口）に広げ、ニッチな話題は本文中の一例・コラム的な言及に留める。「新しくて具体的な事実がある」だけでは主役に足る根拠にならない。

### 4. 執筆（フォーマット厳守 + GEO最適化）
`templates/article-format-sample.html` を必ず読み込み、**このHTML構造・インラインスタイルのルールに厳密に従って**本文を執筆する。新規に別のデザインを考案しない。

**構造ルール（サンプルより）:**
- 全体を同じラッパーdivで囲む
- 冒頭：カテゴリバッジ（丸ピル型、テーマに合う色）＋結論・フックを先出しするリード文2段落
- 背景/基礎知識セクション：`#fdfcf9`系の囲みボックス＋番号付きカード
- 本編の各見どころ：`<h2>`ごとに1セクション、`border-left`の色をセクションごとにローテーション（赤→青→緑→紫...）
- 画像：角丸・枠線・box-shadow、直下に`▲ キャプション`。2枚並べる場合はflexで50%幅
- 豆知識コールアウト：絵文字タイトル付きボックス、テーマ色に合わせた背景/ボーダー
- 記事末尾：必ず`#1a1a1d`背景・`#bfa758`見出し色の「まとめ」セクション

**追加要素:**
- **FAQセクション**：背景知識セクションと同じ「番号付きカード」スタイルで、想定される検索クエリに直接答えるQ&Aを5〜7問。GEO対策として、各回答は単体で意味が通る完結した文にする（AI検索エンジンに引用されやすくするため）
- **具体性**：蔵元名、日本酒度、精米歩合、価格帯、開催期間・場所など、固有名詞と数値をできるだけ盛り込む。値上げ・価格改定のようなテーマでは「約5〜18%」のような抽象的な範囲だけで終わらせず、商品別の「改定前→改定後」の実額を探す（メーカーの公式プレスリリースは範囲しか出さないことが多いが、プライシーやjoylabのような価格改定まとめサイトが商品別の実額表を公開していることがあるので、そちらも検索対象にする）
- **一次情報リンク**：酒蔵・自治体・団体の公式サイトへの外部リンクを適宜含める（`target="_blank" rel="noopener"`）
- **情報量・専門性の厚み**：GEO評価では文字量・情報密度も重要な要素。単一の切り口で終わらせず、以下のような角度を組み合わせてセクションを増やし、本文を厚くする
  - 分類・定義（業界団体や公的な基準があれば一次情報で確認して引用する）
  - 具体的なシチュエーション別の使い分け（例：料理の種類別・温度帯別・シーン別のガイド）
  - 選び方・見分け方のチェックポイント
  - 目安として本文は最低でも6000〜8000文字程度を目安にし、内容が薄いと感じたら「分類」「比較」「具体的な使い分け」のいずれかの切り口を追加できないか検討する

**注意（一般論の埋め草を書かない）**: 「節約術」「選び方のコツ」のようなリスト系コンテンツは、日本酒の実態に即さない一般的なEC系の埋め草（例:「福袋を活用する」「訳あり品をチェックする」）で水増ししない。福袋は在庫処分目的であり実質的な節約にならず、日本酒で「訳あり品」が出回ることは稀——このような一般論は日本酒に詳しい読者からすぐに見抜かれる。日本酒の実態に即した具体例を使う。例（値上げ対策の文脈で検証済み）：
  - 一升瓶（1800ml）を選ぶ（四合瓶より単位あたり単価が安い）
  - 特定名称にこだわりすぎず「普通酒」「本醸造」も選択肢に入れる
  - 蔵元の直販・頒布会を利用する（中間マージンが少ない）
  
  他のテーマでも同様に、一般的なECの通説ではなく「日本酒業界の実態」に基づいた具体策を書く。自信が持てない場合は、無難な一般論で埋めるより先にWebSearchで実態を確認する。

### 5. 楽天商品リンクの挿入
`lib/rakuten.mjs` の `searchItems(keyword, hits)` でテーマに関連する商品（銘柄名、地域名、酒器など）を検索し、2〜4点を本文中の自然な文脈に挿入する。関連記事ボックス（`#f9f9f9`背景・アイコン付き）と同系統のスタイルで、`target="_blank" rel="nofollow sponsored noopener"` を必ず付与する。

```js
import { searchItems } from "./lib/rakuten.mjs";
const items = await searchItems("久保田 純米大吟醸", 3);
```

検索が失敗した場合（例外発生）は、**記事作成自体は止めずに**アフィリエイトリンクなしで進行し、本文末尾に `<!-- TODO: 楽天商品リンクを手動で追加 -->` をHTMLコメントとして残す。

### 6. 画像の挿入
画像は用途によって2つの方法を使い分ける。テキストばかりのセクションが続く場合は、見出しごとに最低1枚は画像を入れて読みやすくする。

**a. サムネイル・イメージイラスト（AI生成）**
記事全体の雰囲気を表すサムネイルや、特定の商品・実物を描かない一般的なイメージ画像は `lib/geminiImages.mjs` の `generateImage(prompt)` で生成する。プロンプトは記事のテーマ・雰囲気に合わせ、実写ではなく水彩画/イラスト調など、サムネとして映える指定にする。

```js
import { generateImage } from "./lib/geminiImages.mjs";
import { uploadImage } from "./lib/githubPublish.mjs";

const buf = await generateImage("日本酒の冷酒とグラス、夏らしい爽やかな水彩画風イラスト");
const url = await uploadImage(buf, "2026-08_夏酒特集_サムネ.png", "feat: 記事用サムネイル追加");
```

**b. 具体的な料理・食材・シーンの実写（Pexels）**
「牛肉」「焼き鳥」「ラム肉」のような一般的な料理・食材・シーンの実写を入れたい場合は、`lib/pexels.mjs` の `searchPhoto(query)` を使う。Pexelsは商用利用・改変可のライセンスで、特定企業や商品の写真ではなく一般的な被写体の検索に使う（特定ニュース記事や企業の商品写真の転載には使わない。その場合は手順6-aのAI生成で代替する）。

```js
import { searchPhoto } from "./lib/pexels.mjs";
const photo = await searchPhoto("grilled beef steak");
```

Pexelsの画像は`imageUrl`を直接`<img src>`に使ってよい（GitHubへの再アップロード不要）。**必ずキャプションに出典を明記する**：

```html
<img src="{photo.imageUrl}" alt="...">
<p style="font-size:12px; color:#666; margin-top:8px;">▲ Photo by {photo.photographer} on <a href="{photo.pexelsUrl}" target="_blank" rel="noopener">Pexels</a></p>
```

**共通の注意**: 画像生成・検索・アップロードが失敗した場合も記事作成は止めず、その画像を省いて進行し、完了報告でその旨を伝える。

### 7. MicroCMSへ下書き作成
`lib/microcms.mjs` の `createDraft(fields)` で下書き保存する。使うフィールドは以下（`article`エンドポイントのスキーマ）：

| フィールドID | 内容 |
|---|---|
| `title` | 記事タイトル（32〜40文字程度、SEO意識） |
| `category` | カテゴリ（過去記事の傾向に合わせる） |
| `content` | 手順4で作ったHTML本文（手順5・6の商品リンク・画像を組み込み済み） |
| `imageUrl` | 手順6のサムネイル公開URL |

`eventDate`等のイベント系フィールドは日本酒イベント記事でない限り送らない（空のまま）。`oldId`も送らない。

**contentId（記事のID）**: 自動採番に任せず、記事テーマを表す英語スラッグを自分で決めて渡す。ルールは英数字小文字と`_`または`-`のみ（日本語・大文字・スペース不可、`^[a-z0-9_-]+$`）。内容が分かる単語を2〜4語程度でつなげる（例: `aged-sake-meat-pairing`, `hiyaoroshi_2026_guide`）。手順1で取得した直近記事のIDと重複しないようにする。

```js
import { createDraft, draftEditUrl } from "./lib/microcms.mjs";
const id = await createDraft({ title, category, content, imageUrl }, "aged-sake-meat-pairing");
console.log(draftEditUrl(id));
```

画像生成が本文執筆後に完了した場合など、既存コンテンツに後から反映したいときは `updateDraft(id, fields)` を使う。この関数は対象が**既に公開済みか**を自動判定し、公開済みならstatusパラメータなしでPATCHして公開中の本体を直接更新、未公開ならstatus=draftを維持する（過去に、公開済み記事へstatus=draft付きでPATCHした結果、別の下書きリビジョンに書き込まれてしまいサイトに一切反映されない事故があったため）。

**ユーザーが既に公開・手動編集した記事を修正する際の注意**: ユーザーがMicroCMS管理画面でその記事の編集画面を開いたままにしていると、画面の自動保存がAPI経由の更新を上書きしてしまうことがある。更新しても反映されない場合は、ユーザーに編集画面を閉じているか確認してもらう。また、更新後は必ず`updatedAt`だけでなく本文の中身（変更箇所の文字列）を再取得して実際に反映されているか検証すること。

### 画像の扱いについての注意
記事のネタ元（プレスリリース・ニュース記事・crowdfundingページ等）に実物写真がある場合でも、**「自由に使用可」と明記されていない限り、その画像をそのまま転載・rehostしない**（著作権リスクを避けるため）。そのようなケースでは実物写真ではなくAI生成イラストで代替する。明記がある場合のみ、出典表記＋リンク付きで元画像を使ってよい。

**ユーザー提供の実写真をアップロードする際のEXIF回転バグに注意**: iPhone等で撮った写真の一部は、ピクセル自体は横向きのまま保存され、EXIFのOrientationタグ（例:6や8）で「表示時にこの向きに回転せよ」と指定する形式になっている。`sips -r`で見た目上の向きを直しても、このEXIFタグは書き換わらずに残ってしまい、サイト側の画像処理がタグに従って二重に回転させてしまうことがある（実際に発生した不具合）。写真の向きがおかしい場合は、`sips -g orientation`だけでなくPython+Pillowの`img.getexif().get(274)`で実際のOrientationタグを確認し、`ImageOps.exif_transpose(img)`で正しいピクセル配置に変換してから、Orientationタグが残っていない状態（`None`または`1`）で保存し直してからアップロードする。GitHubの同じファイル名を上書きしてもCDN/画像最適化キャッシュが古い版を返し続けることがあるため、直した画像は**別のファイル名で再アップロード**して確実にキャッシュを回避する。

### 8. Instagram投稿用キャプション生成
記事が完成したら、Instagram投稿用のキャプション案を作成する。過去実績上、告知用テンプレートカード画像＋告知文の単体投稿はパフォーマンスが低い（プロフィール文＋ハイライト「最新記事」で告知の役割は既に担保されている）。そのため**必ず「短尺版」を基本とし、実物写真・リール（酒瓶、飲食店、乾杯シーンなど）に添える前提**で作る。

重要なのは文字数の短さではなく、**「新着記事のお知らせ」という定型の告知文っぽさを避け、写真に馴染む自然な語り口にすること**。体験談・小ネタ・感想を交えて3〜5文程度に膨らませるのはむしろ好ましい。避けるべきは「タイトル＋URL＋要約＋定型フッター」という構造化された告知フォーマットそのもの。

**これはあくまで「ベース案」であることを完了報告時に明記する。** 記事作成の時点では実際にどの写真・お店・銘柄と組み合わせるか分からないため、投稿前にユーザー自身が実際の体験（訪れた店名・飲んだ銘柄・エピソード等）を足して仕上げる前提で作る。ベース案には固有名詞の当てはめ待ちの部分を残しておいてよい。

**書き出しのコツ**: いきなり要約や結論から入るより、**「〜になってませんか？」のような共感を誘う問いかけ**から始めると自然に読み進めてもらいやすい（例: 「残暑が続くこの時期、ただ冷蔵庫でキンキンに冷やしてそのままだけの飲み方になってませんか？」）。

**短尺版（通常はこちらを使う。実物写真・リールに添える用）:**
```
{共感を誘う問いかけ、または写真の内容に馴染む導入（1文）}

{体験ベースの語り。記事のテーマに自然に触れる。感想や小ネタを交えて自然な文章量で（目安3〜5文程度、短く削りすぎない）。絵文字は控えめに}

詳しくは記事で📝（プロフィールのリンク or ハイライトから）
https://nom2.jp/article/{contentId}

{※実際の写真の場所・銘柄等があれば、ユーザーが個別に追記する欄。@店舗アカウント等もここに入る}

{ハッシュタグ（記事テーマの固定+動的タグに加え、実際に写った店舗・銘柄があれば固有名詞タグも追加）}
```
例（ひやおろしの記事＋酒屋の店頭写真など）:
```
街で「ひやおろし」の文字を見かけたら、もう秋の始まりのサインかも🍁

解禁時期やおすすめの選び方、記事にまとめました📝（プロフィールのリンク or ハイライトから）
https://nom2.jp/article/hiyaoroshi_2026

#日本酒好きと繋がりたい #日本酒雑学 #ひやおろし
```

**長尺版（Stories・ハイライト説明文など、投稿そのものが記事紹介である場合のみ使う。フィードの通常投稿には基本使わない）:**
```
nom2.jp 新着記事👉「{記事タイトル}」📝
https://nom2.jp/article/{contentId}

{記事の内容を2〜3文で要約。読者にとっての実利（選び方が分かる、失敗しない、等）を一言添えて軽いCTAで締める。絵文字1〜2個}

他にこんなテーマについて知りたい！ってのがあったらよかったらコメントで教えてくださいね☺️🙏🩷

_______________
記事はプロフィールのURLやハイライトからも飛べます！
@nihonshu.nomnom 👈他の投稿も見てね

日本酒コンテンツメディア日本酒nom × nom（のむのむ）
https://nom2.jp

{ハッシュタグ}
```

**ハッシュタグのルール（両バージョン共通）**: 合計3〜5個に絞る（多すぎると逆に埋もれて発見されにくくなるため）。
- 固定タグ2個: `#日本酒好きと繋がりたい` `#日本酒雑学`
- 記事テーマに応じた動的タグ1〜3個: 記事の核となる固有名詞・キーワードから選ぶ（例: 熟成酒の記事なら`#熟成古酒`、ひやおろしの記事なら`#ひやおろし` `#秋あがり`）。汎用的すぎて競合が激しいタグ（`#日本酒`単体等）より、具体性のあるタグを優先する。

完了報告では**短尺版を基本として提示し、長尺版は参考として添える**。提示時は「これはベース案なので、実際に使う写真のお店・銘柄・エピソードを足して仕上げてください」と一言添える。

### 8.5 ファクトチェック（公開・完了報告の前に必ず実施）
本文を確定させる前に、記事内の固有名詞・数値をすべて洗い出してチェックする。
- 住所・電話番号・創業年・価格・日本酒度などの数値情報は、WebSearchや一次情報（蔵元公式サイト・団体サイト等）で裏取りする。裏取りできない場合は断定調で書かない。
- **ユーザーから事実の訂正を受けたら、同じ情報が本文中の他の箇所（リード文、背景セクション、FAQ、まとめ等）にも重複して書かれていないか本文全体を検索し、すべて直す。**1箇所だけ直して他を直し忘れる事故が過去に発生している（例: 住所をリード文とキャプションでは直したが、FAQの回答に同じ誤情報が残っていた）。`grep`等で該当キーワードを検索し、修正漏れがないことを確認してから完了とする。
- 修正後は、MicroCMSに実際に反映されたかを本文の中身（変更した文字列）で再取得して検証する（前述の「公開済みコンテンツへのstatus=draft事故」を参照）。

### 9. 完了報告
ユーザーに以下を伝える：
- 作成した記事のタイトルとテーマ選定理由（簡潔に）
- `draftEditUrl(id)` で得られるMicroCMS管理画面の編集URL
- 楽天リンク・画像生成のいずれかが失敗していた場合はその旨と対処（手動追加が必要な箇所）
- **必ず「下書きなので公開前に内容を確認してください」と明記する**
- 手順8で作ったInstagramキャプション案（コピペしやすいようそのままの形で提示する）
